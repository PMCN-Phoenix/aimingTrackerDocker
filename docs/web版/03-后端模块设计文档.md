# 03-后端模块设计文档

## 1. 概述

本文档定义 FastAPI 后端的分层架构、模块职责和依赖方向，保证代码结构清晰、易于维护。

**技术栈**：
- 后端框架：FastAPI
- 数据查询：urllib.request（直接调用 InfluxDB API）
- 数据解析：csv 模块（解析 InfluxDB 返回的 CSV）
- 跨域：CORSMiddleware

---

## 2. 分层架构

```
┌─────────────────────────┐
│    API Layer（接口层）    │  ← FastAPI 路由，处理请求/响应
├─────────────────────────┤
│   Service Layer（服务层）  │  ← 业务逻辑，组合多个查询
├─────────────────────────┤
│ Repository Layer（数据仓库层）│ ← 数据查询，封装 InfluxDB 操作
├─────────────────────────┤
│      InfluxDB（数据库）   │  ← 数据存储
└─────────────────────────┘
```

**设计原则**：
- 上层依赖下层，下层不依赖上层
- API 层只做参数校验和响应封装，不写业务逻辑
- Service 层做业务逻辑，组合多个 Repository 查询
- Repository 层只做数据查询，不写业务逻辑

---

## 3. 模块结构

```
web/backend/app/
├── __init__.py          # 包初始化
├── main.py              # FastAPI 主程序（API Layer）
└── repositories/        # 数据仓库层（Repository Layer）
    ├── __init__.py
    ├── influx_client.py # InfluxDB 客户端
    └── queries.py       # 数据查询函数
```

---

## 4. 各模块职责

### 4.1 API Layer（main.py）

**职责**：
- 定义所有 API 路由
- 处理请求参数校验
- 调用 Service 层获取数据
- 封装统一响应格式（code / message / data）
- 配置 CORS 中间件

**包含的路由**：
- `/api/daylists` - 清单相关接口
- `/api/scenarios` - 场景相关接口
- `/api/health` - 健康检查

**不做的事情**：
- 不直接写 InfluxDB 查询
- 不写复杂业务逻辑
- 不做数据转换（返回原始数据格式）

---

### 4.2 Repository Layer（repositories/）

**职责**：
- 封装所有 InfluxDB 查询操作
- 提供原子化的查询函数（查某个东西）
- 解析 InfluxDB 返回的 CSV 数据
- 处理空数据、错误数据等边界情况

**包含的模块**：
- `influx_client.py` - InfluxDB 客户端，负责建立连接、执行查询、解析 CSV
- `queries.py` - 具体的查询函数，对应每个 measurement 的查询

**不做的事情**：
- 不写业务逻辑（比如"组合多个查询"）
- 不做数据格式化（返回原始数据）
- 不做错误处理（只抛出异常，由上层处理）

---

### 4.3 Service Layer（待新增）

**职责**：
- 组合多个 Repository 查询，完成业务逻辑
- 数据格式化、转换、计算
- 处理复杂业务场景（比如"完成度面板数据"需要组合清单行 + 轮数查询）

**待新增的服务**：
- `daylist_service.py` - 清单相关业务逻辑
- `scenario_service.py` - 场景相关业务逻辑
- `dashboard_service.py` - 看板相关业务逻辑（完成度面板、感悟弹窗等）

**什么时候加**：
- 当 API 层的路由函数里出现了复杂的业务逻辑时，把这部分逻辑抽到 Service 层
- 当多个路由需要共用同一段业务逻辑时，抽到 Service 层

---

## 5. 依赖方向

```
main.py（API Layer）
    ↓ 依赖
repositories/queries.py（Repository Layer）
    ↓ 依赖
repositories/influx_client.py（InfluxDB 客户端）
    ↓ 依赖
InfluxDB 数据库
```

**依赖规则**：
- ✅ API Layer 可以依赖 Repository Layer
- ✅ Repository Layer 内部模块之间可以互相依赖
- ❌ Repository Layer 不能依赖 API Layer
- ❌ 不能反向依赖

---

## 6. 代码规范

### 6.1 命名规范

- 文件名：小写 + 下划线（如 `influx_client.py`）
- 类名：大驼峰（如 `InfluxDBClient`）
- 函数名：小写 + 下划线（如 `get_scenario_best`）
- 常量：大写 + 下划线（如 `INFLUX_URL`）

### 6.2 函数规范

- 每个函数只做一件事
- 函数名要清晰表达用途
- 参数要有类型提示
- 返回值要有类型提示
- 复杂函数要写文档字符串

### 6.3 错误处理

- Repository 层：只抛出异常，不捕获
- Service 层：捕获异常，包装成业务错误
- API Layer：捕获所有异常，返回统一错误格式

## 7. 当前实现状态

| 层 | 状态 | 说明 |
| --- | --- | --- |
| API Layer | ✅ 已实现 | main.py 里的所有路由 |
| Service Layer | ⏳ 未实现 | 当前业务逻辑直接写在 API 层里（代码量小，暂时不需要拆分） |
| Repository Layer | ✅ 已实现 | influx_client.py + queries.py |

**说明**：
- 当前代码量小，业务逻辑简单，暂时不需要拆 Service 层
- 等后续功能多了，业务逻辑复杂了，再拆分 Service 层
- 拆分的时候，把 API 层里的业务逻辑抽到 Service 层即可

## 8. 待优化项

1. **缓存**：清单元数据、基准数据可以加缓存（比如缓存 1 分钟），减少数据库查询
2. **日志**：加日志模块，记录查询时间、错误信息等
3. **配置文件**：把 InfluxDB 连接信息抽到配置文件里，不硬编码在代码里
4. **数据校验**：加 Pydantic 模型做请求参数和响应数据的校验
5. **Service 层拆分**：等业务逻辑复杂了，再拆分 Service 层
