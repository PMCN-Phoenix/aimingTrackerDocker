## 1. 需求对技术栈的三处压力

| 需求 | 原生 Grafana 能不能做 | 说明 |
| --- | --- | --- |
| **A / C 趋势图**（得分 + 命中率 + 目标虚线） | ✅ 完全能 | 现在就是这么做的（timeseries + 常量虚线） |
| **B 的「9 档格子填色表」** | ❌ **做不到** | 原生 Table 只能"按单元格自身数值×阈值"上色。而这里颜色取决于**跨列比较**（分数 vs 各档线），同一格在不同行可能是绿/蓝/灰 → 原生无法表达 |
| **D 的「每日清单 + 卡片式目标对比」** | ⚠️ 能，但只是近似 | 变量 + 行重复已可解决"每天不同清单"；但"上方图表 + 下方对比卡"的观感要靠 table/bargauge 拼，和 Demo 有差距 |
| 清单分层（清单 / 每日清单 / 成绩） | ✅ 与栈无关 | 已在 InfluxDB 用 tag + 独立表实现（`aim_scenario.list`、`aim_daylist`） |

**一句话**：现有栈（InfluxDB + Grafana + Node-RED）覆盖 80%，卡点只有一个 —— **B 的格子表**。

## 3. 四个方案对比

| 维度 | **S1 纯原生 Grafana** | **S2 Grafana + 自绘插件**（推荐） | S3 自建 Web 应用 | S4 混合（Grafana 管 A/C，自建管 B/D） |
| --- | --- | --- | --- | --- |
| B 格子表还原度 | 40%（只能"数字列 + 单色块列"，或把格子值换成 ✓/→/· 状态符号） | **100%**（面板内 JS 渲染 HTML，和 Demo 同款） | 100% | 100% |
| D 卡片还原度 | 70% | **100%** | 100% | 100% |
| 单入口 / 一致性 | ✅ 都在 localhost:3001 | ✅ 同左（还是 Grafana 一个站） | ❌ 多一个站点（端口、登录、导航割裂） | ⚠️ 两个站点，需自行做首页导航 |
| 变量 / 时间范围 / 自动刷新 | ✅ 原生 | ✅ 原生 | ❌ 全部自己写 | ⚠️ 自建侧要自己写 |
| 开发量 | 小 | **中**（写面板 JS + 装插件） | 大（前端 + 后端 API + 部署） | 中偏大 |
| 维护成本 | 低 | 低（配置随 dashboard JSON 一起版本化） | 中高（多一个服务要开机自启/排障） | 中高 |
| 主要风险 | 视觉达不到你要的效果 | 第三方插件升级/兼容 | 长期维护自己写的服务 | 两套并存的心智负担 |
| 技术栈 | 现有 | 现有 + 3 个面板插件（版本 pin） | Python FastAPI + 前端框架/ECharts + 现有 InfluxDB | 两者 |

---

## 4. 推荐：S2（Grafana + 自绘插件）

**理由**
1. **唯一卡点已实测可解**：格子表交给"HTML graphics / Business Text"面板里的一段 JS（就是 Demo 里那套渲染逻辑，直接搬）。
2. **保持单入口**：还是 `localhost:3001`，A/B/C/D 四看板同级互跳；变量、时间范围、自动刷新、告警这些都不用自己造。
3. **数据层零改动**：InfluxDB + Flux + 现有导入链路继续用，`scenario_lists.json`（清单）+ `aim_daylist`（每日清单）照旧。
4. **可回滚**：面板代码随 dashboard JSON 一起 provisioning；万一插件出问题，退回 S1 的妥协版即可（不改数据）。

**落地方式**
```
[原生 timeseries]  A / C 图表、B 顶部分布、D 每条的得分/命中率曲线
[自绘面板]        B 的 4 大类 14 子类格子表（HTML 表格 + 内联样式 + 进度条）
                  D 的"目标分 / 下一档线 / 命中率门槛 vs 现状"对比卡
[原生变量]        D 的 day 变量（默认最新）+ scenario 查询变量 + 行重复
[数据]            InfluxDB（aim_scenario / aim_kill / aim_daylist / aim_daylist_meta）
[导入]            Node-RED（现状）或后续迁 Python（见第 6 节）
```

**插件固定版本（写进 compose，重建容器也不丢）**
```yaml
environment:
  - GF_INSTALL_PLUGINS=gapit-htmlgraphics-panel:2.2.3,marcusolsson-dynamictext-panel:6.3.0
```

## 5. 备选与降级

- **S1 降级版（若插件方案失效）**：B 表用原生 Table —— 9 档列只显示数字，"已达/下一档/未达"用**独立的状态列**（✓ / → / ·，用 Value mappings 上色），另加一列进度条（Bar gauge）。视觉打折，但语义不丢。
- **S4 混合（若你更想要"网页版清单页"）**：B/D 做成独立网页（复用 Demo 前端 + 一个只读 API），Grafana 只留 A/C。适合以后想把"看板"扩展成"随身的训练门户"时再考虑。
- **S3 全自建**：只在 Grafana 完全无法满足时才考虑（目前不是这种情况）。

## 6. 附带议题：导入解析层要不要从 Node-RED 迁到 Python？

| 现状 | 问题 |
| --- | --- |
| 解析逻辑在 Node-RED 的 function 节点里（JS，`aim-import-main` / `aim-analyze-main` / `aim-weekly-main`） | ① 清单白名单等 **3 处硬编码**，改一次要同步三处 ② 改 flows 必须先停容器（否则被内存覆盖）③ 与项目里 7 个 Python 脚本（`sync_lists.py` / `daylist_sync.py` / `tempo_sync.py` / `reflection_table.py` / `aimlab_import.py`）**两套语言并存** |

| 选项 | 好处 | 代价 |
| --- | --- | --- |
| **A. 保持 Node-RED** | 不用动，风险 0 | 上面三个问题一直在 |
| **B. 迁到 Python**（推荐做，但不必现在） | 一个语言、清单从 `scenario_lists.json` 单点读取、随时可改无需停容器 | 一次性改造 + 回归验证 |
| **C. 混合**：新逻辑（daylist、tempo、S2 相关）全用 Python，老的 12 场景逻辑继续 Node-RED | 渐进、风险低 | 仍是两套 |

> 我的建议：**先把 B/D 看板做出来（S2），导入层迁移放到 v0.5**，等 S2 的日常流程跑顺再一次性换掉。
